# NimDaydu 本机测试记录

日期：2026-10-07。机器：Windows 11、Core Ultra 5 125H、32 GB RAM；CPU 推理，未使用 Arc/NPU。浏览器：隔离配置的 Chrome for Testing 154.0.8037.57。测试音频为 Windows System.Speech 英语合成，实际语音文件约 20.595 秒，包含产品名、Discord、日期、Java、GitHub。

这些是功能和性能检查，不是识别/翻译准确率基准，也不是所有会议的延迟保证。没有用真实 Discord/Slack 账号进行长会议验收。

## 原生流式识别对照

版本：moonshine-voice 0.1.5。原生基准输入为约 20.595 秒语音加 2 秒尾部静音，共 22.595 秒。按真实速度重放，通过模型事件记录草稿和定稿。结果在本机忽略目录 `artifacts/benchmark-default.json` 与 `artifacts/benchmark.json`。

| 模型与线程 | 加载时间 | 推理计算 / 重放音频时长 | 首个非空草稿 | 模型标记句尾到定稿 |
|---|---:|---:|---:|---|
| Small，上游默认线程 | 0.858 s | 1.018 | 1.080 s | 2.44–4.63 s，逐渐积压 |
| Medium，上游默认线程 | 约 1 s | 1.034 | — | 存在明显积压 |
| Small，单线程 ORT | 0.512 s | 0.365 | 0.655 s | 0.249–0.723 s |
| Medium，单线程 ORT | 0.734 s | 0.561 | 0.742 s | 短样本可跟上，但更耗计算 |

采用上游提供的 `MOONSHINE_ORT_SINGLE_THREAD=1`，默认 Small。Medium 在同一样本的日期上曾添加错误年份，不能根据模型大小假定更准确。Small 最早的草稿也出现过错误单词 `you`；v0.2 不再把这些草稿显示出来。

本机离线英中模型：Argos en_zh 1.9 / OPUS，CTranslate2 INT8，两个翻译线程。初始四个短句测试，模型加载约 0.326 秒，单句推理约 0.054–0.102 秒。服务与 ASR 分开执行，避免翻译阻塞采音。

## v0.2 完整服务链路

使用 `local-service/benchmark_pipeline.py`，经过实际 WebSocket 协议、真实 Moonshine、句子整理和认证的离线翻译接口。按 80 ms 分帧、16 kHz Float32 真实速度发送，默认整理等待 0.8 秒，尾部添加 3 秒静音。

| 指标 | 本次结果 |
|---|---|
| 实际语音文件时长 | 20.595 s |
| 整理后的句子 | 6 句；均为 final，revision 1 |
| 音频开始到首句中文完成 | 2.835 s；包含说完首句的时间 |
| 模型标记句尾到整理完成 | 1.053–1.395 s |
| 每句离线翻译 HTTP 请求 | 0.036–0.124 s |
| 模型标记句尾到中文完成 | 约 1.124–1.431 s |

整理完成延迟依次为 `1.167, 1.053, 1.340, 1.216, 1.064, 1.395` 秒；翻译耗时依次为 `0.100, 0.071, 0.066, 0.062, 0.124, 0.036` 秒。数据在 `artifacts/benchmark-pipeline.json`。

原先模型将 “Friday” 和 “October ninth” 分成两块，此次整理后为一条完整日期句；“Next” 与后续语句合并。源码也覆盖一个音频片段中的多句、缩写、数字及未说完的短语。这里只是保守规则：连续讲话、标点缺失或语义模糊仍可能分错。时间是模型估计，拆分句按文本长度分配，未手工标注词级真实句尾。

此服务基准不包含 Chrome 播放器的缓冲、侧栏翻译租约或真实网络会议音频的延迟，不能把它当作全平台的端到端保证。

## 实际 Chrome 联调

已通过独立 Chrome 的真实扩展工具栏操作，捕获 `http://127.0.0.1:8800` 中播放的合成 WAV，经过 AudioWorklet 48 kHz PCM、本机 ASR、离线翻译与双语阅读器。该验证不是向 UI 填入假字幕。

- 自动连接：新固定扩展身份通过浏览器真实 Origin 自动获得本机连接令牌；未手工复制令牌。
- 主页面默认中文与英文同时可见，没有草稿译文反复替换，没有配对/模型配置表单。
- 暂停/继续/结束工作，原声继续播放；时间轴包含暂停期间的真实时间，暂停期间不补录。
- 独立设置页打开成功；改变显示方式可同步到已经打开的阅读器，再恢复默认双语。
- 25 秒继续转录检查中，15 条既有译文保持原文与中文不变，字幕总数增加到 22 条；服务快照中没有 partial。结果在 `artifacts/v2-stability.json`。
- 实际点击导出 TXT 和 JSON，两种下载均完成，样本各有 27 句。JSON version 2、final 标志、时间和段落内容检查通过。结果在 `artifacts/v2-exports.json`。
- 最后一次重新加载构建并从头播放，得到 6 个完整译句，日期合并、final/translationRevision 一致及中文句末标点检查通过；记录在 `artifacts/v2-final-browser.json`，界面截图在 `artifacts/v2-reader-final.png` 和 `artifacts/v2-settings.png`。
- v0.1 实际播放时服务工作集曾约 401 MiB；该值是短时观察，未作为 v0.2 长会话资源保证。

源码检查通过：22 个 Python 测试、11 个 TypeScript 测试，以及 TypeScript 类型检查和生产构建。覆盖音频格式/顺序/暂停、单会话锁、Origin/令牌鉴权、默认双语迁移、日期续接、缩写/小数、内部草稿隐藏、译文冻结与按顺序显示。测试服务使用伪引擎，不替代上面的真实模型/浏览器联调。

Chrome Translator API 在测试浏览器中存在，但 TranslateKit 和英中组件为 `0.0.0.0`，语言包创建超时；因此本机 OPUS 是默认方式。DeepSeek 可选接口与保存密钥的权限经过测试，没有配置或调用真实付费 API。

补充（同日）：用户日常 Chrome 在 [Chrome 官方翻译测试页](https://chrome.dev/web-ai-demos/translation-language-detection-api-playground/) 成功将公开样句“你好，世界！这是一个翻译测试。”译为 “hello world! This is a translation test.”，说明这一 Chrome 的中英翻译模型可用。没有完成同句英→中质量对照，也没有借此宣称 NimDaydu 扩展集成已经在日常浏览器验收。旧的两个隔离测试浏览器目录已移至 `.nimdaydu/cache-archive/` 作为可恢复备份；日常浏览器的历史、登录及通用缓存未改动。

## 准确性与下一次验收

样本中的 NimDaydu 被识别为 `Nim Daedoo`，其他重放中 `our` 曾变为 `R`。离线译文有措辞不自然、标点遗漏等情况；v0.2 统一句末标点，但不会补造或纠正不确定的英文词语。显示稳定只解决反复改写的问题，不能证明事实、数字、人名均正确。

平台网址识别已测试 Discord、YouTube、Slack、Google Meet 和通用网站，捕获使用同一套 tabCapture；这不代表逐一完成了这些平台的真实会议验收。

接下来的真实使用检查：

1. 用户自己的 Discord 网页通话和直播，检查口音、专业术语、日期/数字、音量及双语完整性。
2. 常用 YouTube 视频与 Slack 网页会议，验证实际播放器/会议的音频是否可捕获。
3. 连续 30/60 分钟并行通话与采集，观察风扇、CPU、内存、队列和模型稳定性。
4. 长句无停顿、多人打断与噪声时的整理边界，以及关闭来源/关闭所有字幕视图后的清理。

复现指令见 README，原生与完整链路脚本分别为 `benchmark.py` 和 `benchmark_pipeline.py`。
